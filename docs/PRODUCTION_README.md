# DeviceVault Production Deployment

Welcome! This directory contains everything needed to deploy DeviceVault in production across 6 nodes with high availability and horizontal collector scaling.

## Quick Start

### 1. Review Architecture

Start with [PRODUCTION_DEPLOYMENT.md](./PRODUCTION_DEPLOYMENT.md) for:
- 6-node architecture overview
- Component placement and responsibilities
- Design principles (HA, scalability, externalized config)
- Deployment phases and prerequisites

### 2. Prepare Configuration

Follow [PRODUCTION_CONFIG_EXAMPLES.md](./PRODUCTION_CONFIG_EXAMPLES.md) to:
- Understand configuration file formats and options
- Generate initial configs using provided scripts
- Review security best practices
- Set up monitoring

### 3. Deploy Using Scripts

```bash
# Node 1 (Primary Orchestration)
sudo bash scripts/setup-prod-node1.sh node1.internal <db-password> <rabbitmq-cookie>

# Node 2 (Standby)
sudo bash scripts/setup-prod-node2.sh node1.internal <db-password> <replication-password> <rabbitmq-cookie>

# Collector Group 1 (Nodes 3-4)
sudo bash scripts/setup-prod-collector.sh group1 node1.internal node1.internal node1.internal

# Collector Group 2 (Nodes 5-6)
sudo bash scripts/setup-prod-collector.sh group2 node1.internal node1.internal node1.internal
```

### 4. Operate with Runbook

Use [PRODUCTION_OPERATIONS_RUNBOOK.md](./PRODUCTION_OPERATIONS_RUNBOOK.md) for:
- Initial deployment verification
- Service management (start, stop, restart)
- Monitoring dashboards and metrics
- Failover procedures
- Scaling and performance tuning
- Troubleshooting guide

## Architecture at a Glance

```
┌─────────────────────────────────────┐
│  Node 1 (Primary, Active)          │  ← Orchestration + DB + Cache + MQ
│  Django + Nginx + PostgreSQL        │     (Primary instances)
│  Redis + RabbitMQ                   │
└─────────────────────────────────────┘

┌─────────────────────────────────────┐
│  Node 2 (Standby, Cold)             │  ← Replicas (standby, not running)
│  PostgreSQL Replica (read-only)     │     Promotes on Node 1 failure
│  Redis Replica (read-only)          │
│  RabbitMQ Cluster Node              │
└─────────────────────────────────────┘

┌──────────────────┐    ┌──────────────────┐
│  Nodes 3-4       │    │  Nodes 5-6       │
│  Group 1         │    │  Group 2         │
│  Collectors ×2   │    │  Collectors ×2   │  ← Celery workers
│  (3 procs each)  │    │  (3 procs each)  │     (scalable, distributed)
└──────────────────┘    └──────────────────┘
```

**Key Facts:**
- Node 1 runs all application services actively
- Node 2 holds read-replicas, promotes on failure (manual or external automation)
- Collectors on Nodes 3-6 connect to Node 1's broker/cache
- Multiple workers per node allow concurrent processing
- Configuration externalized to `/etc/devicevault/` (no rebuilds needed)

## Key Decisions & Tradeoffs

### 1. No Application-Level HA

**Decision:** Node 2 runs standby DB/cache/MQ replicas, but application (Django/Nginx) stays offline until promotion.

**Rationale:**
- Simpler deployment (no distributed transactions, consensus protocols)
- Easier to reason about (clear primary/standby, no split-brain risk)
- Failover is manual or external (keepalived, cloud LB)

**Tradeoff:** ~30 seconds to few minutes for failover vs. automatic HA in Kubernetes.

**For higher availability:** Use Kubernetes with StatefulSets, or cloud-native managed services.

### 2. Externalized Configuration

**Decision:** All config in `/etc/devicevault/`, mounted into containers.

**Rationale:**
- No Docker rebuilds for config changes
- Secrets stay off images
- Configuration versioning (git/automation-friendly)
- Supports multiple environments from same image

**Security Note:** Protect `/etc/devicevault/` with OS-level ACLs; use external secrets management (Vault) for sensitive values.

### 3. Collector Grouping

**Decision:** Collectors grouped by `CollectionGroup`, each group has dedicated workers on separate nodes.

**Rationale:**
- Isolate load (Group 1 devices won't starve Group 2)
- Parallel processing (multiple workers per node)
- Easy scaling (add nodes to group, adjust docker-compose)
- Flexible deployment (groups on different infrastructure if needed)

**Tradeoff:** Manual routing by collection group. For full load balancing, add Kubernetes Job or distributed job queue layer.

## Deployment Checklist

### Pre-Deployment

- [ ] Provision 6 servers (4+ CPU, 8+ GB RAM each, 100+ GB storage)
- [ ] Install Ubuntu 22.04 LTS (or Debian 12)
- [ ] Install Docker and Docker Compose
- [ ] Set up internal network (10.0.0.0/24 or similar)
- [ ] Configure DNS: node1.internal, node2.internal, etc.
- [ ] Set up shared backup storage (NFS, S3, or Git repo)
- [ ] Prepare SSL/TLS certificates
- [ ] Generate secrets (DB password, Django secret key, RabbitMQ cookie)

### Deployment

- [ ] **Node 1**: Run `setup-prod-node1.sh`, start services, verify health
- [ ] **Node 2**: Run `setup-prod-node2.sh`, start services, verify replication
- [ ] **Nodes 3-6**: Run `setup-prod-collector.sh` for each group, start workers, verify connection
- [ ] **External**: Set up load balancer/keepalived for Node 1 ↔ Node 2 failover
- [ ] **Monitoring**: Set up Prometheus/Grafana or equivalent
- [ ] **Alerting**: Configure alerts for: replication lag, queue backlog, collector health

### Post-Deployment

- [ ] Test failover: Manually promote Node 2, verify collectors reconnect
- [ ] Test backup/restore: Create DB backup, verify restore procedure
- [ ] Load test: Submit collection tasks, verify performance
- [ ] Document: Record actual IP addresses, DNS names, credential locations
- [ ] Train: Walk through operations runbook with support team

## Common Workflows

### Add a New Collector Group

```bash
# Create collectors for Group 3 on Nodes 7-8
sudo bash scripts/setup-prod-collector.sh group3 node1.internal node1.internal node1.internal

# On Nodes 7-8:
docker compose -f docker-compose.prod-collector-group3.yaml up -d
```

Then in DeviceVault UI: Create new Collection Group, assign devices, set `rabbitmq_queue_id = group3`.

### Scale Collectors for Existing Group

```bash
# On Node 3, increase Group 1 workers
# Edit docker-compose.prod-collector-group1.yaml: add celery-worker-4, celery-worker-5, etc.
docker compose -f docker-compose.prod-collector-group1.yaml up -d
```

Verify in Flower: http://node1:5555/ shows new workers connected.

### Enable Backup Encryption

```bash
# Generate encryption key
python -c "import os,base64; print(base64.b64encode(os.urandom(32)).decode())"

# Edit /etc/devicevault/node1/config.yaml
encryption:
  enabled: true
  keys:
    mk-prod-1: <generated-key>

# Restart Django
docker compose -f docker-compose.prod-node1.yaml restart django
```

### Upgrade DeviceVault

```bash
# On Node 1, pull latest code
cd /opt/devicevault/repo && git pull origin main

# Rebuild images
docker compose -f docker-compose.prod-node1.yaml build --no-cache

# Run migrations
docker compose -f docker-compose.prod-node1.yaml run --rm django \
  python manage.py migrate

# Restart
docker compose -f docker-compose.prod-node1.yaml up -d
```

### View Collector Task Status

```bash
# RabbitMQ queue status
curl -u guest:guest http://node1:15672/api/queues | \
  jq '.[] | select(.name | startswith("collector")) | {name, messages}'

# Celery task status
curl http://node1:5555/api/tasks

# Worker status in Flower
curl http://node1:5555/api/workers
```

## Troubleshooting

### "Cannot connect to broker"

```bash
# On collector node, check network
docker exec <worker-container> ping node1.internal

# Check RabbitMQ is running
docker exec rabbitmq-1 rabbitmq-diagnostics -q ping

# Check credentials
curl -u guest:guest http://node1:15672/api/overview
```

### "Database connection refused"

```bash
# Check PostgreSQL is running on Node 1
docker exec postgres-1 psql -U devicevault -d devicevault -c "SELECT 1;"

# Check network from Node 2/collectors to Node 1
docker exec <any-container> nc -zv node1.internal 5432
```

### "Collection tasks stuck in queue"

```bash
# Check for stuck tasks
curl http://node1:5555/api/tasks | jq '.tasks | group_by(.state) | map({state: .[0].state, count: length})'

# Check worker capacity
curl http://node1:5555/api/workers | jq '.[] | {name, concurrency, current_tasks: .pool.max_concurrency}'

# Increase workers if needed (see "Scale Collectors" above)
```

### "Replication lag increasing"

```bash
# Check lag
docker exec postgres-1 psql -U devicevault -d devicevault -c \
  "SELECT NOW() - pg_last_xact_replay_timestamp() AS lag;"

# Check network
docker exec postgres-1 ping -c 5 node2.internal

# Restart replication on Node 2
docker compose -f docker-compose.prod-node2.yaml restart postgres
```
